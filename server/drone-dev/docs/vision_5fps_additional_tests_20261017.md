# HDD 환경 5fps 추가 시험 보고서 v1.0

작성일: 2026-10-17 (Asia/Seoul). 기존 2026-10-16 보고서를 보존한 별도 추가 시험 기록이다.

**판정: 5fps 지속 처리 미달. 입력별 SSH 연결 분리는 저속 동시 입력에서 개선을 확인**

## 조건과 범위

- PC의 사람 포함 UE 녹화 20장을 반복 재생 → SSH 로컬 포워딩 → SIM FastAPI → TensorRT 비전 워커 → 기존 SIM DB를 실제로 통과시켰다. 이번 시험에서 Unreal을 새로 실행하거나 비행시키지는 않았다.
- 원본 1920×1080 JPEG 중앙값 445,817.5바이트. 모델 v12_f91_swa, 임계값 0.20, model_config_id `9e223e9c-bff2-5775-84bf-05b7e93818e2`를 유지했다.
- HDD 저장과 파일/디렉터리 fsync, 서비스 자원 설정, 인증, 대기열 상한 30장을 유지했다. 서비스 코드·DB 테이블·마이그레이션·REAL 업무 데이터 입력을 변경하지 않았다. 기존 SIM DB에 시험용 임무·실행·프레임·관측을 추가했다.
- 15개 실행 각각 입력 구간 60초. 두 입력 시험은 같은 물리 PC의 서로 다른 worker 인증과 임무를 사용한 동시 재생이다. 두 PC·두 Unreal 인스턴스·두 실기체를 검증한 결과는 아니다.
- 현재 API의 duration_s 상한이 60초이므로, 2fps는 60초씩 세 차례 반복했다. 180초 연속 운용 시험은 NOT_RUN이다. 상한을 넘긴 최초 시험 생성 요청은 422로 거절됐으며, 이때 영상 입력은 시작하지 않았다.
- 학교 서버의 인바운드 포트나 방화벽은 추가로 열지 않았다. 시험용 PC 포워딩 포트 18444~18448만 구분했고, 모두 기존 SSH와 동일한 서버 SIM 수신기로 연결했다.
- 외부 BAZE quick 분석은 시험 설계의 교란 요인 검토에만 사용했다. 실행·ID 대조·판정은 로컬/서버의 실제 측정으로 확인했다.

## 통신 경로 비교

기존 공유 SSH에서는 각 1fps 두 입력의 DB 완료가 8장/5장이었고, 새 SSH 하나를 공유해도 10장/9장에 그쳤다. 입력별로 별도 SSH TCP 연결을 사용한 시험에서는 60장/60장을 모두 처리하고 잔여 대기열이 0이 됐다. 기존 연결의 사용 시간만으로 설명되지 않으며, 공유 전송 경로가 악화에 기여했을 가능성을 지지한다. 시험 순서와 배경 부하는 통제하지 않았으므로 SSH 다중화가 유일한 원인이라고 확정하지 않는다.

PC 수치는 같은 PC의 단조 시계로 잰 연결기 API 호출 완료 시간으로, 전송과 PC 측 로그 기록을 포함한다. 서버 수치는 서버 진입 뒤의 처리 시간이다. 서로 다른 시계의 시각을 빼서 종단 지연으로 계산하지 않았다. p95는 원시 요청 소요시간의 보간 백분위로 다시 계산했으며, 원본 client JSON의 과거 요약보다 summary.json을 우선한다.

공유 연결에서는 `408 UPLOAD_TIMEOUT`(약 15초 본문 수신 기한), `503 FRAME_UPLOAD_BUSY`, 일부 `409 MEDIA_BUSY`가 관측됐다. 408은 디스크 저장 단계에 들어가기 전 본문 수신이 기한 내 끝나지 않은 결과다. 기존 HDD 제약만으로 모든 정체를 설명할 수 없다. 소켓 유휴 제한 8초와 서버 본문 기한 15초, 재시도와 잔여 수신 작업의 중첩도 후속 개선 대상으로 남는다.

10초 정지는 업로드 스레드만 의도적으로 기다리게 했고, 별도 명령 조회는 계속했다. 이 조건은 정지 전에도 자연 발생한 시간 초과가 있어 정지의 독립 효과를 추정할 수 없다. 실제 LTE/RF 단절, 패킷 손실, 재접속 적합성 시험으로 취급하지 않는다.

## 서버 부하와 비교의 한계

서버 표본 214개를 약 5초 간격으로 기록했다. GPU 평균 2.9%, 표본 최대 95%, 최대 메모리 2377MiB였다. GPU 사용률은 추론 순간에 높아졌지만 이번 표본의 메모리에는 이전 동시 학습 때의 약 19GiB 점유가 나타나지 않았다. 학습을 시작·중지하거나 자원을 강제로 배정하지 않았다.
I/O pressure some avg10 표본 최대 46.92%, 평균 9.59%; CPU I/O wait 구간 평균 2.53%; sda busy 구간 평균 30.35%였다. 5초 표본은 짧은 정체를 놓칠 수 있고, 시험 도구를 재개하는 동안 표본 공백이 있다.

이전과 같은 입력·fps·서비스 배포본을 반복했지만, 10월 16일의 동시 학습 부하를 재현한 동일 부하 실험은 아니다. 조건은 순차 실행했고 공유 디스크/네트워크 부하는 통제하지 않았다. 압축·해상도 조건은 각 한 번의 표본이므로 인과적인 성능 순위를 부여하지 않는다.

## 데이터 보존과 종료 확인

실패 실행의 PC 대기열 180장을 삭제하지 않았다. 이 중 DB에 아직 없는 생성 입력은 165장이고, 15장은 서버에 저장됐지만 PC가 ACK를 확인하지 못해 재전송 저널에 남은 입력이다. 생성되지 않은 입력 기회는 위 표의 생성 생략에 별도로 기록했다.

로컬 보존 위치: `D:/Capstone1/SITL/NET_SITL/runtime/throughput-20261017/<run_id>/frames/`. 각 JSON에는 고정 frame_id·analysis_run_id·bundle_id·해시가 있으며 JPEG와 함께 남아 있다. 성공으로 바꾸거나 다른 ID로 재생해 원래 실패를 덮지 않았다. 실패한 실행은 FAILED로 남겼고 자동 재전송기를 새로 실행하지 않았다. terminal 실행의 신규 미디어 예약 권한과 재전송 복구 경로는 별도 점검이 필요하다.

DB에 수신된 프레임과 분석 완료 수, 유일 ID 수 및 실제 입력 ID 집합을 대조했다. 부분 실패는 서버에 도달한 집합과 PC 잔여 집합을 구분했다. 모든 수신 분석은 완료됐고 ANALYSIS_FAILED/ANALYSIS_ATTEMPT_FAILED는 0이었다. 수신되지 않은 입력의 성공을 뜻하지 않는다.

최종 SIM/REAL 준비 상태와 코드 해시를 다시 확인했다. 비행 활성화·실기체 활성화는 false를 유지했고, 서버에 접수된 분석의 미완료 작업은 0이다. 최종 정합성 추가 기록은 final-integrity.json에 보관한다.

## 후속 판단

현재 SSH 개발 경로의 5fps와 공유 연결의 동시 입력을 실서비스 준비 완료로 판정하지 않는다. 입력별 전송 연결 분리는 저속 동시 입력에서 효과를 보인 후보이며, 관제 명령/상태와 대용량 영상의 별도 연결 구성도 후속 시험으로 확인할 필요가 있다. Cloudflare Tunnel로 바꾸기만 하면 해결된다는 결론은 내리지 않는다.

HDD의 기록 보장을 유지하면서 요청 속도 제한·재시도 백오프·미확인 입력 복구와 제어/영상 전송 경로를 먼저 보완할 근거를 얻었다. 5fps가 필수라면 원본 영구 저장과 최신 추론 처리의 분리 정책을 추가로 결정하고 검증해야 한다. 이번 시험에서 기록 보장을 끄거나 서비스 코드를 수정하지 않았다.

라이브 UE·실기체·LTE/RF·Cloudflare·동시 학습 부하·장시간 운용·압축 후 탐지 정확도는 NOT_RUN, 정밀 프레임 종단 지연은 NOT_VALIDATED다. 녹화 입력에는 pose가 없으며 공식 좌표를 활성화하지 않았다.
