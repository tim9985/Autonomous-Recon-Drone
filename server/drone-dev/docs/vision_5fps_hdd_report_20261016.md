# 5fps 처리 보강 및 HDD 검증 기록

작성일: 2026-10-16 (Asia/Seoul). 범위: SIM 연결기 → 학교 서버 FastAPI → GPU 비전 워커 → 기존 SIM DB. 서버 저장장치는 HDD만 사용한다. REAL 서비스 파일과 비행 활성화 설정은 이번 배포 대상이 아니다.

## 구현한 변경

- 연결기: JPEG·pose·해시·고정 식별자를 최대 5프레임씩 전송한다. 촬영 간격 기본 0.2초와 대기열 30장 상한을 유지한다. 최대 약 0.8초 모아 보내며, 서버가 정확한 ID 목록을 확인해 줄 때까지 로컬 원본을 보존한다.
- 서버 수신: 인증·실행/임무/세션 권한을 먼저 확인하고 실제 바이트 수와 SHA256을 검사한다. 1회 합계 최대 8 MiB이며 동시 수신은 2개로 제한한다. 각 프레임의 예약·저장 한도와 기존 식별자를 유지한다.
- HDD 저장: 파일별 fsync를 생략하지 않고 최대 5개씩 함께 기다린다. 디렉터리 반영도 완료한 후 DB에서 프레임·분석 작업을 확정한다. 느린 디스크 작업 중에는 DB 전역 쓰기 잠금을 잡지 않는다. 실패한 예약은 용량에 계속 포함되고 같은 ID로 재전송해 복구한다.
- 통신 기록: 이벤트 루프에서 디스크 동기화를 기다리지 않는다. 서로 다른 로그는 최대 4개씩 저장하되 같은 이벤트 ID는 직렬화하고 디스크 반영을 확인한다.
- 비전 처리: 최대 5개 분석 입력의 임대와 최대 5개 결과의 DB 저장을 각각 한 트랜잭션으로 묶는다. GPU 프로세스는 하나이며 프레임을 순서대로 분석한다. 결과는 fsync한 로컬 저널을 먼저 남기고 전송한다.
- 복구: 이전 단일 결과 저널을 먼저 처리한다. 응답 유실 시 동일 묶음을 재전송한다. 손상 입력은 재시도 한도를 거쳐 명시적으로 실패 처리하며 다른 작업을 막지 않는다. 일부 추론이 실패해도 나머지 성공 결과는 보존한다. 영구적인 요청 거부는 검토용 파일로 보관하고, 인증·네트워크·서버 장애는 원본 저널을 유지해 재전송한다.

## API 연결 규격

기존 단일 프레임·예약/업로드/확정 API도 유지한다. 모든 내부 경로는 기존 mTLS와 서비스별 Bearer 토큰을 요구한다. 관제 브라우저가 내부 비전 API에 직접 접속하지 않는다.

| 경로 | 요청과 응답 |
|---|---|
| `POST /device/v1/simulations/runs/{rid}/frames/content` | 헤더 `X-Frame-Metadata`에 base64 JSON `FrameContent`, 본문에 이미지. 성공 201: `{frame_id, analysis_run_id, stored:true}` |
| `POST /device/v1/simulations/runs/{rid}/frames/batch/content` | 같은 헤더에 `{frames:[FrameContent,...]}` 1~5개. 헤더 최대 12,288자. 본문은 순서대로 이어 붙인 이미지, 합계 최대 8 MiB. 각 항목의 `byte_size`로 나누어 검사. 성공 201: `{frames:[확인값,...]}` |
| `POST /internal/v1/analysis-runs/next-input` | 이전 단일 입력 경로. `X-Analysis-Metadata`에 `{job,frame}`, 본문은 이미지 |
| `POST /internal/v1/analysis-runs/next-input-batch?model_config_id=UUID` | 최대 5개. 본문 첫 4바이트는 unsigned big-endian JSON 길이, 다음은 UTF-8 JSON 배열 `[{job,frame,byte_size},...]`(64 KiB 이하), 이어서 이미지들(합계 40 MiB 이하). 유휴 시 JSON `{jobs:[]}` |
| `POST /internal/v1/analysis-runs/completion-batch` | JSON `{results:[{analysis_run_id,result:{claim_id,attempt_no,observations}},...]}`, 최대 5개·5 MiB. 모두 검증하고 커밋한 후 `{completed:[분석ID,...]}`. 하나가 유효하지 않으면 전체 롤백 |

연결기 요청에는 실행을 claim할 때 사용한 `producer_session_id`와 같은 `X-Simulator-Session`을 넣는다. 단일 메타데이터 헤더는 최대 8,192자다. 재시도 때 프레임·분석·미디어·묶음 ID와 본문을 바꾸지 않는다. 수신 시간 제한은 15초다. 409/503/연결 오류 때문에 다른 ID를 새로 만들지 않는다.

## 검증 조건과 합격 기준

실제 학교 서버에 PC의 SSH 터널·mTLS 연결로 전송했다. 실시간 UE CAPTURE와, 사람이 포함된 기존 UE 녹화 프레임의 시간 간격 재생을 구분한다. 녹화 재생은 실제 비행이나 새로운 라이브 장면 검증이 아니다.

5fps 합격 기준은 60초 동안 약 300장 촬영, 대기열 상한에 따른 촬영 생략 0, 종료 시 대기열 해소, 입력 수와 분석 완료 수 일치다. `interval_s=0.2` 설정만으로 합격 처리하지 않는다. 수신 완료와 추론 완료를 별도로 기록한다.

최종 측정 결과는 아래에 기록한다.

**최종 판정: 5fps 지속 처리 미달. 2fps 시연 표본은 촬영 생략 없이 왕복 완료.** 기본 `interval_s=0.2`를 낮추지는 않았으며, 2fps 시험은 별도 실행에서 `0.5`를 지정했다.

| 최종 배포본의 60초 시험 | 저장/분석 완료 | 촬영 생략 | 최대/종료 대기 | 탐지 관측/상태 포함 | 판정 |
|---|---:|---:|---:|---:|---|
| 라이브 UE CAPTURE · 5fps 설정 | 261/261 | 23 | 30/0 | 0/0 | 5fps 미달 |
| 사람 포함 UE 녹화 재생 · 5fps 설정 | 181/181 | 119 | 30/0 | 761/761 | 5fps 미달 |
| 같은 녹화 재생 · 2fps 설정 | 120/120 | 0 | 6/0 | 504/504 | 이 60초 시연 표본 통과 |

261장 및 181장은 5fps 목표 약 300장에 못 미친다. 저장된 입력은 모두 분석 완료했고 분석 실패 이벤트는 0건이었다. 5fps 사람 장면의 추적 ID 포함 관측은 317건, 2fps는 238건이다. 같은 20장의 기존 UE 장면을 반복 재생한 결과로, 탐지·상태 정확도를 새로 평가한 수치는 아니다. 녹화 시험은 pose가 없으므로 좌표는 보류이며, 라이브 시험에는 261장 모두 pose가 저장되었다.

최종 라이브 시험의 명령 조회 응답은 서버 내부 측정 기준 중앙값 약 7.6ms, 95백분위 약 17.8ms였다. 서버 진입 전 LTE/SSH 구간과 실제 제어 반응을 포함하지 않는다.

촬영 PC와 DB 서버 시각을 빼서 얻은 값에는 음수도 나타났다. 따라서 해당 값은 **정밀 종단 지연으로 사용할 수 없으며 NOT_VALIDATED**다. 원본 증거의 시각 차이는 진단 참고값으로만 분리했다. 프레임 수·중복 여부·단일 호스트의 요청 소요시간과 별도로 다룬다. DB `stored_at`도 트랜잭션 시작 시각이므로 커밋 완료 시각으로 해석하지 않는다.

최종 실행 식별자:

- 라이브: run `7d87f2c3-7640-47e0-8ff2-f0b7b40623be`, mission `8f7cf0d5-9926-4c3b-901c-323fbd182c33`.
- 5fps 녹화: run `594a16a5-4ebf-4f10-9bcf-b55465ff7678`, mission `5fb2d75b-9d29-4325-927d-54a5f3d98808`.
- 2fps 녹화: run `4e022730-a7e2-4fb6-a8b4-42072c39b441`, mission `653da2d2-681b-4439-b200-fe6b5c8af77e`.

인증·크기/해시·중간 실패·디스크 반영 실패·중복 재전송·묶음 롤백·손상 입력 복구는 별도 임시 PostgreSQL DB에서 **57개** 확인 후 DB와 저장소를 제거했다. 로컬 계약·워커 회귀 **42개**, 연결기 회귀 **6개 검사 그룹**도 통과했다. OpenAPI SIM 경로는 93개이며, 새 API 계약을 함께 내보냈다.

증거: `D:/Capstone1/Sever/output/throughput-20261016/`의 client/server JSON, acceptance.json, deployment.json, external-review.json. 배포 직전 복구본은 서버 `/home/se/sandboxes/drone-dev/backups/throughput-20261016T122429Z`에 있다. 이 복구본은 바로 전 중간안이며, 최초 작업 전 보관본 등 이전 복구본도 보존했다.

HDD만 쓰는 현재 환경의 파이프라인 시연은 우선 `interval_s=0.5`를 선택할 수 있다. 이 결과는 60초 표본이며 장시간 최저 처리량이나 사람을 놓치지 않는 성능을 보증하지 않는다. 5fps가 반드시 필요하면 실시간 추론과 모든 원본의 영구 저장을 분리하는 정책·구조를 추가로 결정하고 검증해야 한다. 이번에는 프레임 기록 보장을 임의로 바꾸지 않았다.


## 관측한 제한과 해석

서버의 서비스 저장 경로는 회전형 HDD의 ext4에 있다. 측정 중 파일 fsync는 약 25~92ms였고, 별도 표본에서 CPU I/O 대기 13~16%, I/O pressure some avg10 약 39%를 관측했다. GPU 사용률은 96~100%인 구간이 있었으며 학습 작업과 자원을 공유한다. 컨테이너·폴더 분리는 이 물리 자원의 처리량을 보장하지 않는다.

최적화 전후 시험의 배경 부하는 완전히 같지 않다. 수치 차이 전체를 코드 변경의 효과로 단정하지 않는다. 압축률·해상도·탐지 임계값을 임의로 낮춰 목표를 맞추지 않았고, 기록 동기화도 끄지 않았다.

관제 명령 API의 응답이 빠르더라도 영상 결과가 최신이라는 뜻은 아니다. 영상 결과는 촬영 시각과 처리 상태를 함께 확인해야 한다. 대기열이 밀린 결과를 현재 상황으로 취급하거나 자동 경로·비행 판단으로 승격하면 안 된다.

입력 묶음 응답 자체가 유실되면 최대 5개 임대가 만료된 뒤 복구될 수 있다. 프레임 시각이 역행하거나 1.6초 이상 끊기면 연속 추적 상태를 초기화한다. 비행 활성화는 false, 물리 좌표 검증은 보류 상태를 유지한다.

장시간 동시 학습·추론의 최저 처리량 보장, LTE/RF 현장 구간, 실제 프론트 화면, 실기체 비행은 이번 시험의 완료 범위에 포함하지 않는다.
