# REAL 지상 제어·임무 운용 — 2026-11-17

학교 서버의 REAL 서비스와 현장 Pi 실행기를 함께 사용한다. 이번 작업 중 Pi/FC는 연결되지 않았다. 실제 모터·이륙·비행 검증은 하지 않았다. 소프트웨어 시험 통과와 실제 비행 검증을 구분한다.

## 운용 접속

PC에서 기존 SSH 접속에 REAL 포워딩을 포함한다. 외부 SSH 포트는 7540이고, 19443은 서버 loopback의 REAL HTTPS 포트다.

```powershell
ssh -p 7540 -N -L 19443:127.0.0.1:19443 se@<SERVER_HOST>
```

`https://localhost:19443/real-control.html`에서 운용 계정 `dev-operator`로 로그인한다. 개발 CA를 신뢰한 환경을 사용한다. 비밀번호·인증서 개인키·장치 토큰은 이 문서와 설치 묶음에 포함하지 않는다. SIM 서비스(18443)의 동일 이름 계정은 SIM 권한이므로 REAL 운용 주소를 사용한다. `test`는 REAL 로그인 거부를 유지한다.

## 현장 Pi 설치

학교 서버 `export/real-control-gateway-20261117.tar.gz`가 현장 설치 묶음이다. Pi를 연결한 뒤 묶음을 풀고 `install_agent.py --help`로 필수 입력을 확인한다. 실제 FC 연결 경로, 기존 REAL 장치 mTLS 신원 디렉터리, 검증한 배터리 팩의 최소·최대 운용 전압을 지정해야 한다. 수치나 실제 장치 경로를 임의로 채우지 않았다.

설치기는 `/opt/drone-real-agent`, `/etc/drone-gateway/real-control.json`, `/var/lib/drone-real-agent`, `drone-real-control.service`를 만든다. 서비스를 자동 시작하거나 FC 설정을 변경하지 않는다. 사용자는 기존 `gateway`를 기본으로 하며 실제 계정이 다르면 `--user`로 지정한다. 그 계정이 신원 파일과 실제 FC 장치를 읽을 수 있어야 한다. 기본 baud는 57600이므로 실제 KOA 연결 설정과 맞춰야 한다.

장치 신원 디렉터리에는 기존 REAL device 역할의 `ca.crt`, `client.crt`, `client.key`, `token`이 필요하다. 운영자/vision 역할 자격증명으로 대체하지 않는다. FC serial을 읽는 기존 상태 발행기·지상 모터 시험 프로세스는 먼저 중지한다. 새 실행기가 FC를 단독으로 소유한다. 카메라 프로세스는 FC serial을 공유하지 않는 경우 계속 사용할 수 있다. 제어 세션은 기존 카메라/관측 세션과 별개이므로 카메라 세션을 바꾸지 않는다.

Pi에서 학교 서버의 장치 mTLS relay까지 SSH local forwarding을 준비한다. 기본 Pi 접속 대상은 `127.0.0.1:19444`, TLS 서버 이름은 `backend.internal`이다. 예를 들어 Pi의 기존 인증 수단을 이용한 SSH에 `-L 19444:127.0.0.1:19444 -p 7540 se@<SERVER_HOST>`을 포함한다. 기존 터널 포워딩이 있으면 중복 바인딩하지 않는다. TCP 경유 주소와 TLS 서버 이름을 구분해 인증서를 검증한다.

실행기는 ArduPilot quadcopter heartbeat(system 1, component 1 기본값), 새 착륙 상태, GPS 3D fix와 위성 6개, 새 배터리 상태를 요구한다. `FS_GCS_ENABLE=1`, `FS_GCS_TIMEOUT` 5초 이하, `SYSID_MYGCS`가 실행기 GCS ID와 일치, `ARMING_CHECK=1`(전체 검사), `FS_OPTIONS`의 bit 1·4가 꺼져 있는지 읽어 확인한다. 설정이 맞지 않으면 시동/임무 시작을 거부하며 자동으로 값을 덮어쓰지 않는다. RC·배터리·EKF failsafe와 복귀 고도/경로는 현장에서 별도로 확인한다.

설정·serial 독점·신원·시간 동기화를 확인한 뒤 `sudo systemctl start drone-real-control.service`로 상태 연결을 시작한다. 이 동작만으로 FC에 시동·이륙 명령을 보내지 않는다. 자동 시작은 현장 검증을 마친 뒤 운영자가 별도로 결정한다.

## 명령과 임무

1. 운용 페이지에서 LIVE 상태를 확인하고 제어권을 받는다. 제어권은 로그인 세션 단위로 독점되며 2초마다 갱신, 8초 만료된다.
2. 모드 변경, ARM, 지상 DISARM, RTL, LAND를 각각 명시적으로 요청한다. ARM은 모터가 회전할 수 있다. 공중 강제 DISARM과 강제 ARM 값은 없다.
3. 실제 이륙점·경유점을 저장한다. 기존의 최소 15m 상대고도, 이륙점 1km 이내, 예상 900초 이내, RTL 종료 제한을 유지한다. 이 제한은 현장 장애물·배터리 검증을 대신하지 않는다.
4. 임무 업로드 후 FC에서 전체 임무를 내려받아 비교한다. ArduPilot의 seq 0 홈 대체·frame 3/6·float 저장 오차를 구분한다. 기존 계획이 잘못된 비위치 frame을 사용했다면 새 계획으로 다시 저장한다.
5. 현장 관찰자·배터리·지형·새 카메라 영상·모델 입력 사람 25px 조건·실제 복귀 경로·수동 인계 수단을 확인하여 기록한다. 확인은 계획·운용 세션·제어기 세션에 묶이고 120초 유효하다. 이 기록은 운영자 확인이며 자동 센서 검증으로 표시하지 않는다. 기존 카메라/추론 서비스의 기동·영상 정책을 새 실행기가 자동 구성하지 않는다.
6. READY에서 별도의 실제 시작을 누르면 읽기 검증과 새 기체 상태를 다시 확인하고 GUIDED→정상 ARM→임무 시작점→AUTO→MISSION_START를 수행한다. 이륙점과 새 GPS 위치는 20m 이내여야 한다.
7. 명령 접수, 현장 전달, FC 수락/상태 확인, 실행 중, 실제 비행 후 착륙·DISARM을 구분해 표시한다. 결과 미확인은 성공이 아니다. RTL/LAND는 이전 실행을 취소하고 우선 처리한다. ACK가 비행 완료를 의미하지 않는다.

## 단절·복구

전달되지 않은 명령은 8초 만료된다. 현장에 전달된 작업은 디스크에 먼저 기록하여 프로세스 재시작 뒤 재송신하지 않는다. 제어권은 고유 lease ID·사용자 세션·장치 제어 세션에 묶인다. 다른 세션이 제어권을 얻어도 이전 작업 권한이 살아나지 않는다.

상실된 운용 권한으로 GCS heartbeat를 계속 보내지 않는다. FC가 자체 설정된 GCS 단절 동작을 수행한다. 순수 제어권 획득만으로 GCS 감시를 활성화하지 않는다. 기체/프로세스/운용 연결 손실 뒤 결과는 UNKNOWN으로 처리하며 자동 재개하지 않는다. 현장 모드 변경에 의한 RC 인계 감지 후에는 원격 자동 명령을 차단한다. 재개하려면 기체를 안전하게 지상 비무장 상태로 확인하고 실행기 세션을 새로 시작한 후 새 제어권·새 실행 요청을 사용한다.

## 확인 범위와 복구

학교 서버에는 REAL backend/gateway 파일만 백업 후 적용한다. SIM 계정·DB·시뮬레이션 서비스·카메라 설정은 변경하지 않는다. REAL gateway의 공유 httpx 쿠키 저장을 끄고 요청별 사용자 쿠키를 전달한다.

현재 자동 시험은 임시 DB, 가짜 MAVLink FC, 권한 경계와 오프라인 HTTPS에 한정한다. 현장 필수 확인: (1) 프로펠러를 제거한 지상에서 정상 모드/ARM/DISARM 및 수동 인계·단절·재연결 시 재실행 없음, (2) 통제된 현장에서 실제 임무 업로드/읽기 일치·이륙·경유·RTL·착륙과 운용 연결 상실 처리. 두 검증을 마치기 전 실제 비행 성능을 확인했다고 주장하지 않는다.
